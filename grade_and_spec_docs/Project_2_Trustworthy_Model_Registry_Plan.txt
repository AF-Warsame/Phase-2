1. PROJECT_OVERVIEW
    1.1 Objective
        The goal of this project is to design and implement a trustworthy machine learning model registry for ACME Corporation. 
        The registry will extend Beta Software Solutions’ Phase 1 implementation and introduce additional reliability, scalability, and security features. 
        It must support CRUD operations, model ingestion, model rating, lineage tracking, and enumerations while maintaining trustworthiness and reproducibility.
    1.2 Constraints
        The system must be built using AWS free-tier components and comply with Sarah’s baseline and extended requirements. 
        It must support CI/CD, observability, and automated testing. 
        All deliverables must remain within the 90-hour-per-person budget. 
        The team will use another team’s Phase 1 implementation and cannot copy its own codebase.
    1.3 Deliverables
        Delivery 1: Functional CI/CD, baseline CRUD, Ingest, and Enumerate features.
        Delivery 2: Extended features, full testing, observability, and final documentation.
        Postmortem: Analysis of deviations, outcomes, and lessons learned.

2. TOOL_SELECTION_AND_JUSTIFICATION
    2.1 Compute and Hosting
        EC2 for persistent API hosting. Lambda for lightweight background jobs. Both within AWS free tier.
    2.2 Storage
        S3 used for model package and artifact storage due to durability, scalability, and SDK integration.
    2.3 Metadata Store
        DynamoDB for fully serverless, auto-scaling metadata management with zero admin overhead.
    2.4 Logging
        CloudWatch for integrated logging, metrics, and alarms. Connects with SNS for alerts.
    2.5 LLM Integration
        Minimal use of SageMaker endpoint for compliance with the “use LLM” requirement under free-tier constraints.
    2.6 CI/CD Pipeline
        GitHub Actions with OIDC authentication to AWS. Handles automated lint, type checks, unit tests, integration tests, and deployments.
    2.7 Version Control
        GitHub used for version management, collaboration, Dependabot, and CoPilot Auto-Review.
    2.8 Secrets and Credentials
        AWS Secrets Manager for secure handling of credentials and API keys.
    2.9 Budget Control
        CloudWatch Billing Alarm set to alert team when approaching free-tier or budget thresholds.

5. REQUIREMENTS
    5.1 Baseline Functional Requirements
        5.1.1 CRUD Operations
            Authenticated API with default admin user.
            Upload, update, delete, and download model packages (ZIPs and parts).
        5.1.2 Model Rating
            Return Part-1 score plus Reproducibility, Reviewedness, and Treescore metrics.
        5.1.3 Ingest Functionality
            Import HuggingFace models with minimum quality ≥ 0.5 on all non-latency metrics.
        5.1.4 Enumeration and Search
            List registry contents with pagination and regex search. Support version queries with exact, bounded, ~, and ^ symbols.
        5.1.5 Lineage Graph
            Derived from config.json metadata.
        5.1.6 Size Cost
            Endpoint reports model download size.
        5.1.7 License Compatibility
            Verify GitHub repository license compatibility with model license.
        5.1.8 Reset
            Reset endpoint restores registry to empty default state.
    5.2 Interface Requirements
        REST API compliant with OpenAPI schema and a browser-accessible web UI.
    5.3 Non-Functional Requirements
        Single GitHub repository, automated unit + integration + e2e tests achieving ≥60% line coverage minimum.
        GitHub Project Board for milestone tracking and reporting.
        LLM incorporation described in project plan.
        No code copy-paste from open-source; use APIs only.
    5.4 Security Requirements
        Design must mitigate OWASP Top 10 vulnerabilities and follow STRIDE analysis.
        Secure authentication, token management, and input handling.
    5.5 Extended Requirement: High-Assurance Track
        Demonstrate ≥90% coverage for components, ≥95% for full suite.
        Hermetic testing and robust failure handling.
        Disaster recovery from S3/DynamoDB outages.
        Support atomic multi-package transactions.
    5.6 AWS Deployment Requirements
        Must use at least two AWS components and expose a uniform API.
        Implement observability through CloudWatch metrics and a /health endpoint.
    5.7 CI/CD Requirements
        GitHub Actions must automatically test all PRs and deploy to staging upon merge.
    5.8 Accessibility Requirements
        Frontend UI compliant with WCAG 2.1 Level AA standards (ADA compliant).
    5.9 Performance and Monitoring
        CloudWatch dashboards for latency (P50, P95, P99), error rates, queue backlog, and costs.

7. PRELIMINARY_DESIGN
    7.1 Architecture Overview
        Modular microservice architecture hosted on AWS using EC2, Lambda, S3, and DynamoDB.
        REST API Gateway routes to Lambda and EC2 backend functions.
        Frontend hosted via S3 static site.
    7.2 AWS Components
        EC2 for API service.
        S3 for object storage.
        DynamoDB for metadata.
        CloudWatch for metrics.
        Secrets Manager for credentials.
        SNS for alerts.
    7.3 Diagram Description
        Flow: Client → API Gateway → Auth Lambda → EC2 registry API → DynamoDB/S3 → CloudWatch logging.
    7.4 Refinements
        Improved CI gating and earlier integration based on Design HW feedback.

10. LESSONS_LEARNED_FROM_PHASE_1
    10.1 Problems
        Over-ambitious scope, incomplete tests, late integration, and single-owner bottlenecks.
    10.2 Mitigations
        Baseline-first scope control.
        Test-driven development on critical paths.
        Dual ownership per key component.
        CI gating with mandatory lint, mypy, pytest, and reviews.
